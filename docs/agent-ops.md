# Организация работы агентов: tiering, retiering, декомпозиция задач

> **Provenance:** адаптировано из `model-capabilities.md`, `rules-skills-retiering/manifest.md`, `compaction.md`, `sdd.md`, `task-breakdown-template.json` репозитория [SteelMorgan/1c-agent-based-dev-framework](https://github.com/SteelMorgan/1c-agent-based-dev-framework). Статус: **adapted** (2026-08-04). Полный реестр — [external-borrowings.md](external-borrowings.md).

Дополняет операционную модель из `AGENTS.md`. Ключевое отличие контура ИСТК: runtime-тестирование недоступно, поэтому tier-политика опирается на статические gates.

## 1. Уровни риска задач ИСТК

| Уровень | Примеры | Статический gate (обязателен) | Runtime (deferred) |
|---|---|---|---|
| T0 | Правки документации, AGENTS.md, спеки | — | — |
| T1 | Локальное изменение одного модуля/отчёта | bsl-ls 0 errors + cf-validate | — |
| T2 | Несколько модулей, миграция запросов, СКД | bsl-ls + cf-validate + RLM cross-refs + query-review + review по чек-листу | Запуск в базе при появлении контура |
| T3 | Обновление релиза, смена модели типовой, деструктивные операции | всё из T2 + red-verify (второй независимый проход) | Обязательная проверка пользователем на эталонных данных |

Уровень фиксируется в карточке задачи. Для T3 запрашивается подтверждение оператора перед выполнением (см. `AGENTS.md`, «деструктивные операции»).

## 2. Маршрутизация моделей (tiering)

Правила (адаптация `model-capabilities.md`):

- **Ревьюер не слабее автора** — независимая проверка (red-verify, `/verify`) выполняется моделью той же или более высокой категории
- **Explorer/исследование** — дешёвая модель (большой объём чтения, RLM-обходы)
- **Реализация** — рабочая модель по сложности кейса
- **Эскалация** — после N неудачных попыток (по умолчанию 2) задача возвращается оператору, а не мучается дальше
- **Cross-provider** — для критичных T3 допустимо ревью другой моделью/провайдером

## 3. Retiering: guardrail / триггер / навык

Правила всегда-включены в контекст стоят дорого (каждый токен запроса). Адаптация `manifest.md`:

- **GUARD** (guardrail) — всегда целиком: границы записи (main/Extentions/), префикс `но`, запрет `ё`, деструктивные операции. Живут в `AGENTS.md`.
- **TRIG** (триггер) — одна строка «событие → навык/чек»: «после edit 1С-кода → 1c-check», «при изменении СКД → skd-validate». Короткие, всегда в контексте.
- **SKILL** (тело-процедура) — загружается лениво по описанию: `1cskills`, `istk-rules`, `1c-review-checklist`, `query-review.md`.
- **GOAL/WF** — само-вызов по намерению или запуск из workflow.

Не раздувать always-on канал: новые правила добавляются как TRIG или SKILL, а не как большой текст в `AGENTS.md`.

## 4. Против деградации после компакта (compaction)

- Ключевые правила (границы записи, обязательные проверки) — в начале контекста (`AGENTS.md`)
- После компакта агент перечитывает `AGENTS.md` и durable state текущей задачи. `docs/1c-specs-index.md` читается только при задаче по XML-спекам
- Триггеры и чек-листы — «тонкие»: ссылки на файлы, а не содержимое
- При длинной сессии — ранний автокомпакт, состояние фиксируется в `openspec`-кейсе (progress.md/tasks.md), а не только в памяти

## 5. Шаблон декомпозиции задачи

Адаптация `task-breakdown-template.json` под OpenSpec (карточка в `openspec/changes/<кейс>/tasks.md`):

```json
{
  "spec": {
    "id": "<openspec-change-id>",
    "title": "Краткое название кейса",
    "link": "openspec/changes/<кейс>/proposal.md",
    "summary": "1-2 предложения сути"
  },
  "tasks": [
    {
      "task_id": "TASK-001-T1",
      "task_type": "code | metadata | report | extension | docs | verification",
      "tier": "T0|T1|T2|T3",
      "depends_on": [],
      "spec_refs": ["openspec/changes/<кейс>/specs/<спека>/spec.md"],
      "deliverables": ["Что будет создано/изменено (пути main/...)"],
      "done_criteria": [
        "bsl-ls 0 errors (команда)",
        "cf-validate 0 errors",
        "RLM: вызываемые объекты существуют",
        "runtime-проверка (deferred): ..."
      ]
    }
  ]
}
```

Принципы (из `sdd.md`):
- Спека до кода: задача ссылается на конкретную спеку через `spec_refs`
- Каждая задача — независимо верифицируемый результат, не «нарезанная по файлам»
- `depends_on` — реальный порядок выполнения, ациклический
- Для T2/T3: `done_criteria` содержит статический gate + явный deferred-runtime пункт

## 6. Правило/навык/воркфлоу

- **Правило** задаёт обязательную рамку (границы, обязательные проверки)
- **Навык** даёт способ (как делать СКД, как править расширение)
- **Workflow** связывает: кейс → задачи → выполнение → верификация

Смысл правил формулирует человек, агент структурирует. Новые правила не добавляются «по ощущению» — сначала кейс, потом обобщение в ревью.

## 7. Классификация задач: short/full

> **Provenance:** `framework/workflows/quick-fix` + `framework-bootstrap` SteelMorgan. Статус: **adapted** (2026-08-04).

- **Short (quick-fix)** — правка <20 строк, 1 файл, без новых объектов метаданных, без архитектурных изменений. Цикл: Найти → Исправить → **Проверить**. Один агент, без кросс-ревью.
- **Full** — всё остальное: новые метаданные, изменение потока данных, архитектура, сомнение. Требует: спека (openspec) → разбиение → реализация → независимая проверка.

Guard-verify: **проверка обязательна даже для self** (1c-check + cf-validate + RLM). Если проверить невозможно — явно зафиксировать риск, молчаливый пропуск запрещён. Превышение границ short → принудительный full.

## 8. Skill-reading protocol

> **Provenance:** `framework/rules/skill-reading-protocol` SteelMorgan. Статус: **adapted** (2026-08-04).

- На старте сессии — прочитать frontmatter/описания задействованных скиллов (`name`, `description`), полное тело — **лениво** при применении
- Правила из AGENTS.md и guardrail'ы — целиком в начале контекста
- «Навык упомянут, но не применён» = нарушение протокола
- После компакта — перечитать ключевые правила (см. §4), а не полагаться на память

## 9. Реестр лимитов самовосстановления

> **Provenance:** `framework/rules/self-recovery-limits` SteelMorgan. Статус: **adapted** (2026-08-04).

| Действие | Лимит |
|---|---|
| Исправление собственного кода (developer) | 2 попытки |
| Итерации BLOCK-замечаний ревью на scope | 3 |
| Гипотезы отладчика | 5 (+3 = максимум 8) |
| Цикл баг → фикс → баг | 2 |

После исчерпания — bug-report/эскалация оператору, а не бесконечный ретрай.

## 10. Контекстные файлы-статусы задач (durable state)

> **Provenance:** `framework/subagents/*` (протокол `task_dir/.context/{role}-context.md`) + `agent-context-protocol`. Статус: **adapted** (2026-08-04).

- Состояние задачи — в репозитории (openspec tasks.md + `.context/`), не в памяти сессии
- Каждый агент/этап пишет: статус (`completed` / `clarification_needed` / `blocked` / `test_failure`), выполненные шаги, команды, свидетельства, следующий шаг
- Смена агента/сессии = чтение последнего статуса, продолжение, а не повтор
- Это механизм, закрывающий «обрыв сессии»

## 11. Cross-provider ревью через Codex CLI

> **Provenance:** `SPEC-codex-review.md` + `tool-usage/review/cross-provider-review` SteelMorgan. Статус: **adapted** (2026-08-04) — Codex CLI доступен в контуре.

- Для T2/T3 и сомнительных мест — независимое ревью вторым агентом через **Codex CLI** (`codex exec`, read-only sandbox)
- Промпт ревьюеру: «Задача + Артефакт (diff) + Чек-листы» (см. `docs/1c-review-checklist.md` §1-§4)
- Ревьюер не слабее автора; вывод — BLOCK/WARN/INFO (см. §5 чек-листа)
- Мониторинг результата через файл вывода; интеграция с картой capabilities — `docs/capability-map.md` §5

## 12. Планирование и выполнение через OpenSpec

- Исследование требований: openspec-explore / opsx-explore.
- Согласованный объем изменения: openspec-propose / opsx-propose; proposal, design, specs и tasks хранятся в openspec/changes/<id>/.
- Реализация: openspec-apply-change / opsx-apply с обязательными 1С-проверками по типу задачи.
- Завершение: openspec-archive-change / opsx-archive после проверки результатов.
- Для short сохраняется цикл из §7. Для full нужны спека, задачи и независимое ревью.
- Тиры T0–T3, статические gates и deferred-runtime сохраняются.
- Старые Memory Bank и XML-планы сохранены как исторические артефакты. DevRails/GRACE gates и синхронизация этих артефактов для новых задач не требуются.
