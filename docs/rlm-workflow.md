# Работа через RLM

Общий порядок для Codex и Kilo. Источник: [rlm-tools-bsl AGENT_INSTRUCTIONS](https://github.com/Dach-Coin/rlm-tools-bsl/blob/master/docs/AGENT_INSTRUCTIONS.md) и [HELPERS](https://github.com/Dach-Coin/rlm-tools-bsl/blob/master/docs/HELPERS.md), адаптировано 2026-10-03. Контракт установленного сервера важнее примеров из upstream master.

## Контракт и начало сессии

- Использовать подключенные MCP-инструменты. Если нужного инструмента нет, проверить endpoint из [mcp.md](mcp.md); при доступном сервере использовать HTTP MCP через shell. Отсутствие инструмента в сессии не означает, что сервер остановлен.
- При HTTP fallback выполнить MCP initialize и notifications/initialized, передавать полученный Mcp-Session-Id, если сервер его выдал. Для POST задать Accept: application/json, text/event-stream. Схему получить через tools/list; ответы разбирать согласно фактическому Content-Type (JSON или SSE).
- Начать с rlm_start(query=..., project="istk") либо точного path. Сверить схему доступного инструмента; не передавать параметры только потому, что они есть в свежей документации.
- Если схема поддерживает domains и slim-режим требует выбор: domains=[] для ядра/одного метода; нужные домены для узкой задачи; "весь каталог" для полного разбора. При поддержке догружать domains ближайшим rlm_execute; подписи из ответа использовать в следующем вызове.
- Проверить index и warnings из rlm_start. Отдельный запрос состояния индекса нужен только при нехватке этих данных.
- rlm_help вызывать при неясном контракте или необходимости рецепта. Если описание текущего инструмента требует справку перед нетривиальным запросом, выполнить это требование. Не переносить правила нового slim-режима на старый сервер вслепую.

## Выполнение

- Объединять связанные операции в rlm_execute: найти → прочитать нужные совпадения → напечатать сводку. Число хелперов не квота; зависимые дальнейшие шаги выбирать по результату.
- Сохранять полные результаты в переменных сессии, повторно одинаковые данные не запрашивать. Печатать нужные поля, счетчики и найденные фрагменты. При усечении вывода уменьшить печать или разбить работу.
- Промах структурного хелпера перепроверить search/git_search в нужном срезе. Ошибку инструмента отличать от пустой выдачи.
- Поведение логики подтверждать телом процедуры. Для проведения проследить подписки и вызовы до фактического исполнителя, включая общие модули и перехваты расширений.
- Завершить rlm_end после последнего обращения к данным сессии, до финального ответа. Отчеты сохранять обычными файловыми инструментами.

## Охват и отрицательные выводы

Перед выводом «отсутствует» или «полный список» при необходимости запросить rlm_help(section="coverage"), если секция поддерживается. Учитывать доступные признаки:
- source — происхождение данных; owner — принадлежность строки main/extension; extensions_included — учет источников расширений. Последний признак сам по себе не доказывает полный охват всех расширений. Legacy scope не заменяет эти оси.
- truncated/has_more/content_truncated — усечение/страницы; partial и причины — неполнота конкретного ответа; index_coverage — охват соответствующего индексного домена.
- index_status=ok и partial=False сами полноту не доказывают. stale_age означает возраст, stale_content — расхождение с диском; disabled/unavailable/build_unproven/wider_than_current требуют учитывать границу покрытия.
- Пустой полнотекстовый результат тоже не доказательство отсутствия при неполном охвате. Указать проверенный корень/срез и ограничения.
- Индекс — снимок: после edit критичные факты сверять с живым исходником. Пересборку/обновление выполнять в разрешенном объеме, соблюдая approval_required текущего сервера. После обновления индекса переоткрыть RLM-сессию.
- Схема старого сервера не дает признаков полноты — проверить первоисточник или явно объявить ограничение; отсутствие поля не считать признаком полного ответа.
