# Контексты выполнения и настройки модулей

Применять при выборе директивы, создании общего модуля или изменении клиент-серверной границы. Размещение предметной логики — [методы](1c-methods.md); назначение событий — [события](1c-events.md).

## Рецепт выбора контекста формы

1. Определить данные: элементы UI, данные формы или явно переданные значения.
2. Выбрать контекст по таблице. Передавать минимальные данные; пакетировать работу одного пользовательского действия.
3. Проверить доступность каждого вызываемого API именно в выбранном контексте и версии платформы.

| Метод управляемой формы | Когда применять | Доступ / стоимость |
|---|---|---|
| `&НаКлиенте` | UI, команда, пользовательское взаимодействие | Клиентский контекст; работу с БД делегировать серверу |
| `&НаСервереБезКонтекста` | Расчет/чтение по явным параметрам | Контекст формы недоступен; форма не передается |
| `&НаСервере` | Действительно требуется чтение/изменение данных или элементов формы | При вызове с клиента передается контекст формы |
| `&НаКлиентеНаСервереБезКонтекста` | Общий для двух сторон алгоритм без данных формы | Исполняется на стороне вызова; каждый используемый API должен быть доступен там |

Локальное предпочтение: если достаточно одного реквизита, передать его в `&НаСервереБезКонтекста`. Если метод перестраивает форму, использовать `&НаСервере`, а не имитировать контекст десятками параметров.

```bsl
&НаСервереБезКонтекста
Функция СуммаСНалогом(Знач Сумма, Знач Ставка)
	ПроцентовВЕдинице = 100;
	Возврат Сумма * (1 + Ставка / ПроцентовВЕдинице);
КонецФункции
```

Пример показывает границу; чистую арифметику обычно оставить на клиенте/в общей функции, без отдельного серверного вызова. У серверных методов формы, вызываемых с клиента, неизменяемые внутри входные параметры объявлять с `Знач`. `Знач` выражает входной контракт; особенности изменяемых коллекций — [методы](1c-methods.md).

У каждого метода формы явно указать одну директиву. Директива `&НаКлиентеНаСервере` относится к модулю команды, не к управляемой форме. У команды `ОбработатьКоманду` выполняется на клиенте; доступные директивы команды: `&НаКлиенте`, `&НаСервере`, `&НаКлиентеНаСервере`. В серверном методе команды контекста формы нет. Методы общего модуля доступны согласно его свойствам; там допустимы `&НаКлиенте`/`&НаСервере`, но для одноконтекстного модуля избыточны по стандарту.

## Общие модули: четыре стандартных профиля

Флаги задают контекст; суффикс описывает назначение. Имя само по себе не переключает исполнение. Таблица — стандарт разработки, не перечень всех технически допустимых комбинаций платформы.

| Профиль | Клиент управляемый | Сервер | Внешнее соединение | Клиент обычный | Вызов сервера | Суффикс |
|---|---|---|---|---|---|---|
| Серверная реализация | нет | да | да | да | нет | Без суффикса; `Сервер` при конфликте имен |
| API для клиента | нет | да | нет | нет | да | `ВызовСервера` |
| Клиент | да | нет | нет | да | нет | `Клиент`; для глобального — `Глобальный` |
| Общий алгоритм | да | да | да | да | нет | `КлиентСервер` |

Рецепт `ВызовСервера`: выделить небольшой экспортный фасад для фактических клиентских вызовов; реализацию оставить в серверном модуле. Передавать сериализуемые значения/ссылки; изменяемые прикладные объекты (`ДокументОбъект`, `СправочникОбъект`) обрабатывать внутри сервера. Это ограничение не запрещает переносимые структуры и массивы. Проверять права на действие и возвращаемые данные на сервере; доверять клиентскому отбору как проверке прав нельзя. `Привилегированный` — отдельное решение безопасности, не способ исправить доступность вызова.

Пример: `ноРасчетыВызовСервера.Рассчитать(Параметры)` принимает клиентский контракт, вызывает `ноРасчеты.Рассчитать(Параметры)` и возвращает разрешенный результат. Это имена проектируемых модулей, не API платформы. Для серверной подписки, получающей объект, использовать серверную реализацию с выключенным `Вызов сервера`.

## Препроцессор

Для модулей объекта и менеджера ИСТК применять обертку всего модуля:

```bsl
#Если Сервер Или ТолстыйКлиентОбычноеПриложение Или ВнешнееСоединение Тогда

// Методы и области модуля.

#КонецЕсли
```

В общем одноконтекстном модуле контекст задать флагами. В `КлиентСервер` хранить одинаковый алгоритм; различающиеся реализации вынести в `Клиент`/серверный модуль. Ветвление по виду клиента внутри клиентского модуля допустимо, если соответствующий API действительно доступен. Условия и области не разрывают выражения или объявления методов.

## Стоимость и проверка

Серверную работу записи формы выполнять в штатном серверном событии, а не отдельным вызовом из клиентского `ПередЗаписью`/`ПослеЗаписи`. Для повторяемых дорогих чтений рассмотреть модуль повторного использования с узким набором ключей; определить допустимость устаревания. Константные дешевые вычисления кеша не требуют; время жизни кеша не считать гарантией между версиями.

Проверить: свойства XML модуля соответствуют профилю; фасад имеет реальных клиентов; внеконтекстный метод не обращается к форме; BSL-LS без severity 1; под обычной ролью нет утечки. Число вызовов, трафик и кеш проверять runtime при доступном контуре; до этого — статическая оценка.
